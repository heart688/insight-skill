# 让真实问题、核心 insight 和全文记忆点连成一条线

用于确立主故事、重写引言逻辑、统一全文记忆点或审查叙事偏移。不绑定领域、模型或论文类型；下列关系按真实贡献选择，不要求每篇论文都有旧方法失效、两个模块或固定段数。

## 先写出核心矛盾

从材料中用普通语言回答：任务需要什么；现有合理做法依赖什么；当前环境或约束使这项依赖遇到什么困难；为什么直接修正仍不容易。核心矛盾是这些事实之间的关系，不是“研究很重要”“已有方法不足”或“我们缺一个新模块”。

可用下面的骨架自检，正文不必照搬：

> 在条件 C 下，目标需要能力 A。已有做法通常依赖依据或过程 B 来实现 A。C 使 B 出现具体困难 D，而限制 E 又使直接修正困难。因此，需要研究怎样在这些条件下实现 A。

其中每个重要连接都应有材料、文献、诊断、逻辑或理论依据。不把常用做法一概写成错误；指出它在原设置中解决了什么，以及当前条件具体改变了哪一环。理论、资源或规模研究可分别用未解命题、缺少的资源和未知的可行边界构造问题，无需伪造失效故事。

问题出现前，读者至少应知道：

- 这里需要什么能力，为什么值得研究；
- 当前通常怎样实现，它为什么合理；
- 当前任务约束使哪一项依赖难以继续成立；
- 这如何影响目标，以及为什么不能轻易修好。

让读者先接受困难，再提出回应它的 insight 和方法。观察名称、模块名和参数方案过早进入，会让读者觉得问题是为方法临时制造的。

## 让“问题真实存在”有适当依据

区分三个层次：

1. **现象可见。** 真实案例、数据分布或动机图显示差异、冲突或瓶颈；示意图只能解释其含义。
2. **困难有机制。** 解释现有依赖如何与任务约束发生冲突，导致信息不足、错误决策、资源成本或其他具体后果。
3. **判断有检验。** 受控对照、干预、理论推导或系统测量，检验所提出的原因与处理原则。

个别曲线可以说明一种现象确实出现，不能自动证明它普遍存在，更不能单独证明它导致性能下降。没有相应对照时，将后果表述为合理风险或待检验问题。不要用反复强调、强烈形容词或问题名替代证据。

## 从核心矛盾提炼 insight

Insight 给出处理困难的一项可理解、可检验的判断：应改变什么依据、共享什么对象、拆开什么职责、控制什么瓶颈，或在哪些条件下采用哪种处理方式。它应在公式和模块名出现前就讲得通。

内部先写两句：

> 核心问题：在什么条件下，哪项现有依赖限制了什么能力？
>
> 核心 insight：改变哪项选择，为什么可能恢复或改善这项能力？

再检查 insight 是否回答了刚才的问题。若问题讲环境异质，insight 突然讲参数冻结；或问题讲延迟瓶颈，insight 突然讲编码器容量，应补上真实关系或把细节降为下一级设计。不要为了串故事添加未实现的机制。

## 固定术语，让每次出现都推进理解

起草前维护一份简短的内部用词记录：主要现象、核心障碍、insight、主要机制分别叫什么。只记录论文真正需要的概念，不再创造额外缩写。准确区分有技术差异的对象，不能为了统一措辞混为一谈。

对同一个核心对象，优先保留同一个英文词或短语；核心问题句在不同章节可以接近统一，只为语法和阅读层次作必要调整。不要为了避免重复把一个概念依次改称为几个听起来相近的概念。术语一致有助于记忆，句子承担的论证任务仍应不同。

在有用的位置复现核心术语：

- **标题与摘要：** 让读者知道任务、具体障碍及回答方向；摘要先交代为什么需要该回答，再进入关键方法。
- **引言问题段：** 从共同认识和常用做法推进到具体困难；观察与约束共同引出研究问题。
- **引言 insight 与方法预告：** 用固定术语给出回答，再解释它需要哪些能力，以及各设计怎样实现。
- **相关工作结尾：** 收束已有工作共同完成了什么，指出本设置中仍需处理的具体障碍，再自然引出本文方向。不能暗示列出的所有方法都具有同一个缺陷。
- **方法概述：** 首句把方法接回核心问题，再按真实信息流展开。不要让模块清单替代研究原则。
- **关键实验解释：** 用最有判别力的对照接回原问题，说清它支持了核心判断的哪一部分；主表排名本身不能证明机理。
- **结论：** 以证据支持的范围回答开头问题，让读者再次得到同一个核心认识。

这些位置不是每篇必须逐项填齐的模板，也不要求每段写一次关键词。若全文已有很多核心词，仍缺乏记忆点，优先检查关键转场有没有说明问题、方法与证据的关系。

## 让模块和实验服务同一个主故事

明确三个层级：

```text
主问题与 insight：本文改变了哪项研究判断或设计原则
→ 实现需求：为落实该原则，需要什么信息、能力或计算性质
→ 操作与证据：模块怎样提供这些能力，哪些对照检验其贡献
```

由一个主问题产生多个具体需求是自然的；不要把每个统计量、损失项、适配方案和效率实现都提升成同等级创新。概述先建立主原则，细节按“当前需求 → 操作 → 产生的信息 → 下一步需求”逐步出现。标准实现正常命名，不靠模块数量制造深度。

实验可以依次建立整体表现、关键选择的贡献、实际信息使用以及适用条件。每组结果选择能回答本段问题的观察，说明它怎样支持主故事。保留比较范围：单方向对照、局部样本、原生工作负载和匹配配置分别支持相应条件下的结论，不能因术语统一就把结论扩大。

## 完稿时检查读者能留下什么

暂时遮住模型和模块名称，仅读摘要、引言收束、方法概述、最关键实验及结论，检查能否回答：

1. 具体问题是什么，为什么在当前约束下真实而值得解决？
2. 核心 insight 是什么，怎样回应这个问题？
3. 方法的关键选择为何从该 insight 产生？
4. 哪项证据最能区分该判断与合理替代解释？

再检查核心问题和 insight 是否始终使用稳定术语，次要设计是否遮住主问题。若只记得方法缩写或模块清单，优先修复转场和主句；若证据不支持原判断，收窄或修正判断。不要通过更多加粗、口号、重复次数或更强措辞补救。
